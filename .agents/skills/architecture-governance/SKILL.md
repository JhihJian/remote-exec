# 架构治理

先阅读根 `AGENTS.md`、`docs/architecture/AGENTS.md` 和当前变更。根据任务选择维护或检查流程。

## 核心动作约束

系统目的、领域对象、外部契约、能力声明或关键测试前提可能变化时，先使用项目内 `.agents/skills/system-constraint-governance/SKILL.md` 分析影响。顶层能力只有用户在当前任务明确要求时才能建立、修改或退役；下层行为和测试可在不改变父能力语义时维护。

## 只读检查

本流程不修改架构文档、状态记录或业务实现。

1. 运行只读检查 `node .agents/architecture-governance/check-state.mjs check`；项目需要确认生效基线时追加 `--require-active`。
2. 按项目 `docs/architecture/AGENTS.md` 检查结论是否位于归属章节、文档归属、读者可理解性、依据定位和关键待确认事项。检查总览是否有 C4 Component 图：系统或容器边界是否明确，项目内组件是否表达职责而非文件/import，连线是否写明运行时、数据、事件、协议或协作语义，且每个项目内组件是否映射到仓库相对目录和关键文件。
3. 报告当前状态、缺失结论、失效依据和关键待确认事项。检查失败时只说明修复条件，不将失败说成架构已经生效。

## 建立和维护

没有现有说明时，从代码、配置、测试和已确认业务资料调查事实。

1. 判断系统目的、模块职责、所有权、依赖、失败语义、信任边界、核心流程或长期业务约束是否变化。
2. 在唯一负责的文档位置说明已确认事实。总览只保留系统目的、稳定边界和主要模块，模块或实现细节按读者需要下沉。总览必须维护一张 C4 Component 图：组件表达稳定职责，连线表达运行时、数据、事件、协议或职责协作，并在图旁映射每个项目内组件对应的仓库相对目录和关键文件。不要将 import、文件依赖或完整调用链画成组件图。每项状态条目使用稳定 `id`、完整结论、归属文档角色和可定位的代码、测试或已确认资料；结论原文放在该角色文档指定锚点的章节中，依据不能指向状态文件自身。
3. 无法确认的影响记录为待确认事项；本地调查可将状态设为 `candidate` 并标记关键事项。完成审阅且没有关键待确认事项时设为 `active`。已建立核心约束时，按 `.agents/architecture/system-constraints.json` 维护 MVP、顶层能力、下层行为、依据和行为测试映射。
4. 项目需要确认架构基线可用于交付时，运行 `node .agents/architecture-governance/check-state.mjs check --require-active`；是否作为合并条件由项目自身流程决定。

删除或重命名依据文件时，移除失效引用并重新确认仍成立的结论。除总览必备的 C4 Component 图外，其他图表仅在能降低理解成本时维护。
