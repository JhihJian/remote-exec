# 架构文档

本目录保存项目当前架构的正式说明。本文件定义文档归属、证据要求和审阅约定。

## 文档归属

- `.agents/architecture/state.json` 中 `overview` 角色指定架构总览，负责系统目的、稳定边界、主要模块、阅读路径和长期业务约束。
- 模块设计、跨模块流程和实现参考按读者需要拆分；接口、字段、配置、事件和源码映射留在实现契约，不堆入总览。
- 重要选择的原因、备选方案和代价由项目已有的决定负责位置承担；已安装决定治理时由对应 Agent Note 负责。

状态记录是证据账本，不是架构正文。每项事实只在一个负责位置完整说明，其他位置使用摘要和链接。

## 总览架构图

每份 `overview` 架构总览必须包含一张架构图，优先使用分层图表达职责和向下依赖。图应明确所描述的进程或系统边界，节点表示稳定职责层次或组件。进程外的调用方、部署关系和运行环境用简短文字解释；需要说明具体跨边界协作时再补充专门图。

每个项目内组件必须在图旁或紧随其后的映射表中关联仓库相对的代码目录和至少一个关键文件。一个组件可以对应多个目录或文件；目标架构中的未实现组件必须明确标注为目标，并给出计划落点。

分层图应说明上层可使用下层、是否允许跨层，以及箭头表示依赖方向而非请求执行顺序。相邻层的连线可由图例统一说明，省略通用跨层依赖；关键跨层行为在正文交代。协作图的连线标注运行时调用、数据交换、事件、协议或职责协作的语义。源码 import、文件引用和完整调用链留在实现说明中。代码目录、关键文件、职责或交互发生实质变化时，同步维护图和映射。

## 基线状态

`.agents/architecture/state.json` 的每个条目必须有唯一 `id`、完整 `conclusion`、归属 `documentRole` 和至少一条 `evidence`。结论必须原文出现在该角色文档指定 `anchor` 的章节范围内；依据必须指向代码、测试或已确认资料，不能指向状态文件自身。`candidate` 仅用于本地调查，`active` 基线不得包含关键待确认事项。

## 长期业务约束

架构总览中的“长期业务约束”只收录项目领域特有、跨多个需求版本仍然成立，且违反后会改变核心业务结果或领域对象语义的规则。规则必须有当前代码、有效测试或已确认业务资料支持，并能用业务语言表达。

通用架构原则、实现机制、校验细节、通用认证授权、运维门禁、接口 Schema 和测试步骤不属于长期业务约束。没有合格规则时省略该章节；状态账本中的 `guarantee` 结论也不能直接等同于顶层约束。

## 核心动作约束

核心约束由项目架构文档的唯一正式位置完整说明。顶层能力共同还原 MVP，数量由项目决定；下层行为描述顶层能力在不同条件下的正常结果和变体结果。鉴权、协议协商、内部处理、分类、判断、评分、可靠性机制和结果变体归入下层，除非它们本身构成面向用户的独立能力。

顶层能力按自身产生的业务产物命名，不以鉴权、协议或可靠性机制命名。

`.agents/architecture/system-constraints.json` 是约束账本，记录 MVP、规则正文的位置、意图依据、现状依据、下层行为和行为测试映射，不重复架构正文。`active` 顶层能力必须有正常行为和变体行为，每项行为各有一条可定位测试。测试名称、调用步骤和实现细节留在账本与测试文件，不写入规则正文。

只有用户在当前任务明确要求时，才改变顶层能力或生命周期。未获授权的实现任务应保持既有顶层能力，运行或修复对应行为测试，并报告潜在影响。下层行为和测试不得扩大、放宽或改写父能力语义。

## 模块审阅

新建或实质性调整模块时，先说明设计结论、要解决的问题、与现有模块的交互和必须保持的规则。只保留能帮助读者理解边界的内容。

读者仅阅读该审阅层，应能判断设计解决的问题、主体和资源关系、协作边界、不可放宽的规则，以及首版不覆盖或尚待确认的事项。目标设计必须明确标注尚未实现；既有模块仅在新建或实质性调整时按此结构演进。
